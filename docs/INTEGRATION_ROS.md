# Интеграция модуля детекции в ROS-пайплайн

Инструкция для встраивания части проекта, отвечающей за детекцию дорожных
повреждений и придорожной инфраструктуры, в ROS-ноду.

**Коротко:** на вход кадр (numpy BGR), на выход обработанное изображение и список
детекций. Обработка в реальном времени невозможна — см. раздел 6, там замеры.

---

## 1. Что делает модуль

Два независимых источника объектов:

| Источник | Чем детектится | Что находит |
|---|---|---|
| **damage** | 5 специализированных YOLO-моделей | продольная / поперечная / крокодиловая трещина, яма, разметка |
| **infra** | OWL-ViT (детекция по текстовому описанию) | дорожные знаки, столбы и фонари, светофоры, люки и решётки |

Поверх любого из них можно получить точную маску объекта: бокс детектора
передаётся в SAM (Segment Anything) как промпт, и SAM обводит объект по контуру.
Альтернатива — «наивная» маска, где бокс просто закрашен целиком.

Итоговая картинка бывает двух видов: рамки поверх исходного кадра либо маски
на чёрном фоне.

## 3. Как встраивать — Python API

**Главное правило: не запускайте CLI на каждый кадр.** `camera_tools/process_frame.py`
загружает модели заново при каждом старте — на Jetson это ~7 секунд. Для ноды
используйте класс `FrameProcessor`: модели грузятся один раз в конструкторе.

```python
from frame_processor import FrameProcessor

proc = FrameProcessor(kind="masks", pipe="pipe3")   # один раз при старте ноды
result = proc.process(frame_bgr)                     # на каждый кадр

result.image          # np.ndarray BGR — готовая картинка того же размера, что вход
result.items          # список найденных объектов
result.damage_items   # только повреждения покрытия
result.infra_items    # только инфраструктура
```

Каждый элемент `result.items` — это `ProcessedItem`:

| Поле | Тип | Смысл |
|---|---|---|
| `label` | `str` | класс, как его назвала модель (`"Pothole"`, `"road sign"`, …) |
| `score` | `float` | уверенность 0..1 |
| `box_xyxy` | `np.ndarray` | `[x1, y1, x2, y2]` в пикселях кадра |
| `color_bgr` | `tuple` | цвет класса в палитре (см. раздел 5) |
| `source` | `str` | `"damage"` или `"infra"` |
| `model_key` | `str` \| `None` | для damage — какая из 5 моделей сработала |
| `mask` | `np.ndarray` \| `None` | bool-маска `HxW`, если режим её строит |
| `mask_score` | `float` \| `None` | уверенность SAM, если маска от него |

Если нужна не готовая картинка, а сырые данные для своих сообщений — берите
`items` и игнорируйте `image`. Отрисовку можно вызвать отдельно:
`FrameProcessor.render_boxes(frame, items)` и `FrameProcessor.render_masks(shape_hw, items)`.

### Формат кадра

Ожидается **BGR** (соглашение OpenCV), форма `(H, W, 3)`, `dtype=uint8`.
Из ROS через `cv_bridge`:

```python
frame_bgr = bridge.imgmsg_to_cv2(msg, desired_encoding="bgr8")
```

Обратно:

```python
out_msg = bridge.cv2_to_imgmsg(result.image, encoding="bgr8")
out_msg.header = msg.header      # сохраните исходный штамп времени
```

Если передать RGB, детекция формально отработает, но качество упадёт — модели
обучались на правильном порядке каналов.

### Скелет ноды (ROS 2, rclpy)

```python
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import Image
from cv_bridge import CvBridge

from frame_processor import FrameProcessor


class DefectDetectionNode(Node):
    def __init__(self):
        super().__init__("defect_detection")
        self.bridge = CvBridge()

        # Модели грузятся здесь, один раз. На Jetson это ~7 секунд —
        # нода будет недоступна в это время, это нормально.
        self.get_logger().info("Загрузка моделей…")
        self.proc = FrameProcessor(kind="masks", pipe="pipe3")
        self.get_logger().info("Модели загружены")

        self.busy = False          # обработка не поспевает за камерой (см. раздел 6),
                                   # поэтому кадры, пришедшие во время работы, пропускаем
        self.pub = self.create_publisher(Image, "~/processed", 1)
        self.create_subscription(Image, "/camera/color/image_raw", self.on_frame, 1)

    def on_frame(self, msg):
        if self.busy:
            return                 # осознанно теряем кадр, очередь не копим
        self.busy = True
        try:
            frame = self.bridge.imgmsg_to_cv2(msg, desired_encoding="bgr8")
            result = self.proc.process(frame)
            out = self.bridge.cv2_to_imgmsg(result.image, encoding="bgr8")
            out.header = msg.header
            self.pub.publish(out)
        finally:
            self.busy = False


def main():
    rclpy.init()
    rclpy.spin(DefectDetectionNode())
    rclpy.shutdown()
```

Обработка занимает ~0.5-1.9 с на кадр, поэтому она **заблокирует** поток
исполнителя. Если нода делает что-то ещё, выносите обработку в отдельный
поток/callback group, а кадры складывайте в очередь глубиной 1 с вытеснением.

## 4. Режимы

Задаются двумя параметрами конструктора: `kind` (что показывать) и `pipe`
(каким пайплайном; только при `kind="masks"`).

`kind`:

| Значение | Результат |
|---|---|
| `"boxes-damage"` | рамки повреждений поверх оригинала |
| `"boxes-infra"` | рамки инфраструктуры поверх оригинала |
| `"boxes-all"` | рамки обоих источников |
| `"masks"` | чёрный фон, цветные объекты |

`pipe` (только с `"masks"`):

| Значение | Повреждения | Инфраструктура |
|---|---|---|
| `"pipe1"` | точные маски SAM | маски SAM |
| `"pipe2"` | заливка бокса | маски SAM |
| `"pipe3"` | точные маски SAM | — |
| `"pipe4"` | — | маски SAM |
| `"pipe5"` | заливка бокса | — |
| `"pipe6"` | — | заливка бокса |

Эквивалентная явная форма — `damage=` и `infra=` со значениями `"seg"`, `"box"`, `"off"`.
Например, `pipe="pipe1"` ≡ `damage="seg", infra="seg"`.

Прочие параметры конструктора: `threshold` (порог YOLO, по умолчанию 0.25),
`infra_threshold` (порог OWL-ViT, 0.15), `weights_dir`, `sam_checkpoint`,
`sam_model_type`, `infra_texts` (свой список классов инфраструктуры), `device`
(`"cuda"` / `"cpu"`, по умолчанию автоопределение).

## 5. Палитра

Цвет закреплён за классом и не зависит от кадра и порядка детекций.

**Повреждения покрытия:** красный — яма, пурпурный — крокодиловая трещина,
жёлтый — продольная трещина, голубой — поперечная трещина, зелёный — разметка.

**Инфраструктура:** оранжевый — знак, синий — столб/фонарь, фиолетовый — светофор,
белый — люк/решётка.

Палитры намеренно не пересекаются: в совместном режиме объекты двух пайплайнов
должны быть различимы. Точные значения BGR — в `yolo_pipeline.MODEL_KEY_COLORS_BGR`
и `mask_pipeline.INFRA_COLORS_BGR`.

## 6. Производительность: почему в реальном времени не выйдет

Замерено на **Jetson AGX Orin**, кадры 1920×1080, 8 кадров, с прогревом CUDA,
на простаивающей машине.

| Режим | Время на кадр | FPS |
|---|---|---|
| 5 YOLO-моделей (боксы, без сегментации) | 0.42 с | 2.4 |
| 5 YOLO-моделей + SAM (точные маски) | 1.09 с | 0.9 |
| OWL-ViT, инфраструктура (боксы) | 0.15 с | 6.7 |
| **Полный цикл (`pipe1`)** | **1.27 с** | **0.8** |

Загрузка моделей — 6.8 с, однократно при старте.

**Вывод.** Съёмка ведётся на 6 FPS, то есть на кадр отводится 166 мс. Полный цикл
занимает 1.27 с — в **8 раз** медленнее. Даже самый лёгкий режим (только боксы
YOLO) — 0.42 с, всё ещё в 2.5 раза медленнее съёмки. **Обрабатывать каждый кадр
в темпе съёмки невозможно.**

Две оговорки к цифрам:

1. В замере полного цикла инфраструктура на тестовом материале не нашлась, поэтому
   SAM для неё не запускался. Когда в кадре есть знаки и столбы, добавится ещё
   ~0.64 с — итого **~1.9 с/кадр**, то есть в 11 раз медленнее съёмки.
2. Машина при замере простаивала. Одновременная запись видео и работа остального
   ROS-графа отберут часть ресурсов, реальные цифры будут хуже.

### Что с этим делать

- **Обрабатывать не каждый кадр.** Рабочая схема прямо сейчас: очередь глубиной 1
  с вытеснением (как в скелете выше) — нода берёт свежий кадр, когда освободилась,
  остальные пропускает. Фактическая частота выхода составит 0.8-2.4 кадра/с
  в зависимости от режима.
- **Выбирать режим по задаче.** Если точный контур повреждения не нужен, `pipe5`
  (заливка боксов) втрое быстрее, чем `pipe3` с сегментацией.
- **Не поднимать лишние модели.** При `damage="off"` YOLO-модели не грузятся,
  при `infra="off"` не поднимается OWL-ViT — и память, и время экономятся.

### Известный резерв по скорости (пока не сделано)

- **Двойной прогон SAM.** Сейчас у пайплайна повреждений и пайплайна инфраструктуры
  свои экземпляры SAM, и каждый отдельно кодирует один и тот же кадр. `set_image`
  стоит 0.64 с и в полном цикле вызывается дважды. Общий экземпляр срежет ~0.64 с
  (1.9 → 1.27 с).
- **TensorRT для YOLO.** Пять моделей гоняются последовательно, пятью отдельными
  проходами — это основная стоимость режима damage. Перевод в TensorRT на Jetson
  обычно даёт 2-4-кратное ускорение (0.42 → ~0.15 с).

Даже с обеими оптимизациями полный цикл до 6 FPS не дотянет — реалистичный
потолок около 2-3 FPS. А вот режим «рамки повреждений в темпе съёмки» после
TensorRT станет достижимым.

## 7. На что обратить внимание

- **Python-окружение.** Модуль живёт в venv `~/workspace/.venvs/detection`
  (Python 3.8, torch от NVIDIA). ROS-нода должна запускаться в окружении, где
  доступны и `rclpy`, и эти зависимости. Проще всего — прокинуть `PYTHONPATH`
  на site-packages этого venv либо собрать ноду так, чтобы она использовала
  его интерпретатор. Ставить torch заново через pip **нельзя**: обычная сборка
  с PyPI не поддерживает CUDA на Jetson и ломает окружение.
- **torchvision собран из исходников.** Штатное колесо с PyPI несовместимо с
  NVIDIA-сборкой torch: не грузятся C++ операции, из-за чего падает NMS в YOLO.
  Пересобранное колесо лежит в `~/workspace/torchvision_build/dist/`, сломанная
  версия сохранена как `~/workspace/torchvision-0.16.1-broken-backup.tgz`.
  Если будете переустанавливать окружение — ставьте torchvision из этого колеса,
  а не из интернета.
- **Первый кадр медленнее.** Прогрев CUDA: первый `process()` занимает примерно
  вдвое больше времени, чем последующие. Если это мешает, прогрейте пустым
  кадром при старте ноды.
- **Дубли между пайплайнами.** В совместных режимах (`pipe1`, `pipe2`) один объект
  может быть найден обоими источниками. Подавление пересечений сейчас работает
  только внутри группы из 5 YOLO-моделей, между damage и infra его нет —
  это осознанное решение, отложено до оценки качества на реальном материале.
- **Пустой результат — не ошибка.** Если ничего не найдено, `process()` вернёт
  корректное изображение (чистый оригинал для рамок, чёрный кадр для масок)
  и пустой `items`.
- **Качество на инфраструктуре не проверено.** На имеющихся записях нет знаков,
  фонарей и светофоров, так что ветка OWL-ViT проверена только на работоспособность
  (механика, палитра, сегментация), но не на качество распознавания. Возможно,
  понадобится подобрать `infra_threshold` под реальный материал.
