# Одиночные снимки с точной меткой времени

`camera_tools/capture_realsense_shot.py` — съёмка отдельных кадров вместо видео,
с максимальной частотой потока и меткой времени из часов камеры.

Про запись видео целиком — `record_realsense_raw.py`, он остаётся как есть.

---

## 1. Чем отличается от того, что было

Прежние инструменты (`record_realsense_raw.py`, `capture_realsense_rgb_photo.py`)
берут кадры через V4L2 обычным `cv2.VideoCapture`. Для видео этого достаточно, но
через V4L2 недоступны две вещи, которые нужны сейчас: часы камеры и управление
выдержкой. Новый скрипт работает через SDK (`pyrealsense2`).

| | старое (V4L2) | новое (SDK) |
|---|---|---|
| Выбор потока | по эвристике над `/dev/video*` | `rs.stream.color` явно |
| Частота | 6 Гц по умолчанию | максимум для разрешения (1920x1080 → 30 Гц) |
| Выдержка | как решит драйвер | предел или фиксированное значение |
| Метка времени | нет | часы камеры + метаданные кадра |
| Результат | видеофайл | отдельные кадры без потерь + JSON + `index.csv` |

Побочный эффект: пропадает старая проблема с выбором ноды. ИК-модуль D415 отдаёт
похожие форматы, и `capture_realsense_rgb_photo.py` до сих пор может выбрать
`/dev/video4` вместо RGB-ноды `/dev/video6`. Здесь поток запрашивается по типу,
подменить его нечем.

## 2. Запуск

```bash
# посмотреть, какие режимы вообще есть у камеры
python3 camera_tools/capture_realsense_shot.py --list-profiles

# превью + снимок по пробелу (1920x1080 @ 30 Гц, выдержка ограничена 8 мс)
python3 camera_tools/capture_realsense_shot.py ../outputs/shots

# съёмка на ходу: фиксированная выдержка 1.5 мс
python3 camera_tools/capture_realsense_shot.py ../outputs/shots --exposure-us 1500 --gain 64

# 60 Гц ценой разрешения
python3 camera_tools/capture_realsense_shot.py ../outputs/shots --width 960 --height 540

# один кадр без окна и выход — для SSH и скриптов
python3 camera_tools/capture_realsense_shot.py ../outputs/shots --once
```

Через `make` (на локальной машине добавьте `PYTHON=python3`, по умолчанию путь
указывает на venv Jetson):

```bash
make shots PYTHON=python3
make shots PYTHON=python3 SHOT_EXPOSURE_US=1500
make shot-once PYTHON=python3
make shots-profiles PYTHON=python3
```

Клавиши в окне: **пробел** — снимок, **Q** — выход.

### Параметры

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--width` / `--height` | 1920 / 1080 | Разрешение. Проверяется по списку профилей камеры. |
| `--fps` | 0 | 0 — взять максимум для этого разрешения. |
| `--exposure-us` | 0 | 0 — автоэкспозиция. Иначе фиксированная выдержка в мкс. |
| `--ae-limit-us` | 8000 | Верхний предел выдержки для автоэкспозиции. 0 — без предела. |
| `--gain` | -1 | Усиление при ручной выдержке, 0–128. -1 — не трогать. |
| `--warmup-frames` | 30 | Кадры на сходимость автоэкспозиции и привязки часов. |
| `--burst` | 1 | Сколько кадров подряд сохранять по одному нажатию. |
| `--once` | — | Без окна: снять и выйти. |
| `--format` | png | `png` или `tiff`, оба без потерь. |
| `--calib` | — | Если задан, рядом сохраняется undistort-копия. Исходник остаётся. |

## 3. Смаз: причина не в частоте кадров

Смаз даёт **выдержка**, а не частота. Частота влияет косвенно: автоэкспозиция не
может держать выдержку дольше периода кадра. На 6 Гц период — 166 мс, и в тени
или в пасмурную погоду автоматика спокойно выбирает выдержку в десятки
миллисекунд. Отсюда и смазанные снимки.

Смаз в пикселях считается так:

```
смаз = скорость [м/с] × выдержка [с] / масштаб [м на пиксель]
```

Пример при масштабе 2 мм на пиксель (кадр 1920 px покрывает ~3.8 м поперёк дороги):

| Выдержка | 20 км/ч (5.6 м/с) | 60 км/ч (16.7 м/с) |
|---|---|---|
| 166 мс — предел на 6 Гц | 460 px | 1385 px |
| 33 мс — предел на 30 Гц | 92 px | 276 px |
| 8 мс — наш предел по умолчанию | 22 px | 67 px |
| 2 мс | 5.6 px | 17 px |
| 1 мс | 2.8 px | 8 px |

Масштаб зависит от установки камеры; замените его на свой и пересчитайте — формула
линейная.

Выводы:

* Переход с 6 на 30 Гц уменьшает худший случай в 5 раз, но сам по себе задачу не
  решает: 276 px смаза на 60 км/ч всё ещё много.
* Приемлемый результат даёт выдержка порядка **1–2 мс**, а это уже ручной режим
  или жёсткий предел автоэкспозиции.
* Короткая выдержка требует света. Днём на открытой дороге запаса хватает, в тени
  и в сумерках придётся поднимать `--gain` и мириться с шумом. При съёмке на ходу
  предсказуемый шум лучше непредсказуемого смаза: шум детектор переживает,
  смазанную трещину он просто не увидит.
* Опция `auto_exposure_priority` выставляется в 0 — иначе автоматика при нехватке
  света снижает реальную частоту кадров вместо того, чтобы поднять усиление.

**Отдельно: rolling shutter.** У D415 цветной сенсор со строчной развёрткой.
Строки кадра считываются последовательно, поэтому на скорости прямые линии
наклоняются, и короткая выдержка этого не исправляет — она убирает смаз внутри
строки, а не расхождение между строками. Для измерения размеров дефектов по кадру
это систематическая ошибка. Связано с пунктом про rolling shutter в
[OPEN_ISSUES.md](OPEN_ISSUES.md).

## 4. Метка времени

Скрипт включает у сенсора `global_time_enabled`. В этом режиме librealsense
непрерывно сопоставляет часы камеры с часами хоста и выдаёт метку уже в
календарной шкале. Проверить, что получилось, можно по строке в выводе — она
печатается один раз для первого кадра:

```
Метки времени первого кадра:
  домен: global_time
  источник: global_time: часы камеры, приведённые librealsense к времени хоста
  метаданные кадра: actual_exposure, actual_fps, backend_timestamp, frame_counter,
                    frame_timestamp, gain_level, sensor_timestamp, time_of_arrival
```

Домен может быть трёх видов, и разница принципиальная:

| Домен | Что означает | Годится для синхронизации |
|---|---|---|
| `global_time` | часы камеры, приведённые к времени хоста | да, это рабочий режим |
| `hardware_clock` | сырые часы камеры, начало отсчёта произвольное | да, но нужна своя привязка к эпохе |
| `system_time` | часы хоста в момент приёма кадра | нет: это момент приёма, а не съёмки |

**Если домен оказался `system_time`** — часы устройства недоступны. В Linux
метаданные UVC требуют патча ядра из librealsense
(`scripts/patch-realsense-ubuntu-lts.sh`). Без него метка отстоит от реального
момента съёмки на десятки миллисекунд и «плавает» под нагрузкой: на 60 км/ч
50 мс — это почти метр по маршруту. Скрипт в таком случае печатает
предупреждение и продолжает работу.

### Что сохраняется

Рядом с каждым кадром `shot_ГГГГММДД_ЧЧММСС_ммм.png` пишется одноимённый `.json`:

```json
{
  "unix_time_s": 1755500000.123456,
  "unix_time_iso": "2026-08-18T07:33:20.123456+00:00",
  "time_source": "global_time: часы камеры, приведённые librealsense к времени хоста",
  "timestamp_domain": "global_time",
  "frame_timestamp_ms": 1755500000123.456,
  "frame_number": 42,
  "host_realtime_s": 1755500000.2,
  "host_monotonic_s": 123.4,
  "host_minus_device_ms": 76.5,
  "metadata": {
    "frame_timestamp":  {"value": 1755500000123456, "unit": "us"},
    "sensor_timestamp": {"value": 1755500000120000, "unit": "us"},
    "time_of_arrival":  {"value": 1755500000200,    "unit": "ms"},
    "actual_exposure":  {"value": 2000,             "unit": "raw"},
    "frame_counter":    {"value": 301,              "unit": "count"}
  }
}
```

Сырые метки сохраняются вместе с приведённой намеренно: если привязка к эпохе
окажется неточной, по `frame_timestamp` и `host_realtime_s` её можно перестроить
задним числом, не переснимая материал.

Дополнительно все снимки попадают строками в `index.csv` в той же папке — чтобы
сопоставлять с треком и облаком точек без разбора отдельных JSON.

## 5. Синхронизация с лидаром и координатами

Три источника времени в проекте идут по разным часам: камера, лидар и базовая
станция. Что даёт этот скрипт и что остаётся сделать:

* **Даёт:** метку камеры в шкале хоста плюс сырые часы устройства — то есть
  кадр можно поставить на общую ось времени.
* **Остаётся:** привязать к той же оси лидар и координаты. Практический
  минимум — синхронизировать часы хоста по NTP или PPS от приёмника, тогда
  `global_time` окажется в той же шкале, что и метки базовой станции.
* **Проверить:** остаточное расхождение стоит измерить один раз на характерном
  объекте, а не считать нулевым.

Это ровно тот пункт, который в [OPEN_ISSUES.md](OPEN_ISSUES.md) записан как
рассинхрон источников времени.

## 6. Ограничения

* На момент написания камера не была подключена к машине, поэтому скрипт проверен
  статически: разбор профилей, выбор частоты, запись кадра, JSON и `index.csv` —
  на синтетических данных; наличие всех используемых имён API — в установленной
  сборке `pyrealsense2`. Работу с живой камерой нужно подтвердить: первый запуск
  покажет реальный домен меток времени и набор доступных метаданных.
* Единицы `actual_exposure` в метаданных зависят от прошивки, поэтому значение
  сохраняется как есть, с пометкой `raw`.
* `sensor_timestamp` и `frame_timestamp` относятся к разным точкам тракта
  (считывание сенсора и часы устройства). Какая из них ближе к середине выдержки —
  нужно проверить на своей прошивке, прежде чем закладывать поправку.
* Скрипт не пишет глубину и не выравнивает потоки: снимается только цветной кадр.
